## Learning objectives

Distinguish JSON mode from schema-constrained output, design bounded schemas, and validate data before application use.

## Prerequisites

Know basic TypeScript and how to describe desired output in a prompt.

## Theory

Many applications need machine-readable output: classification labels, product attributes, or action plans. Asking a model to “return JSON” does not guarantee valid JSON or the correct structure.

**Structured Outputs** guides a model to produce output that conforms to a supported JSON Schema. It constrains structure and types, but does not verify facts, business consistency, or access rights. The application must still check these before using output to trigger side effects. [OpenAI: Structured Outputs](https://platform.openai.com/docs/guides/structured-outputs)

## Architecture

```text
Input → model with output schema → parse/validate → business rules → side effect
                                         └→ controlled error / retry policy
```

Distinguish format errors, refusals, business-rule failures, and transport errors. Successful JSON parsing alone should not trigger a sensitive action.

## TypeScript example with Zod

```ts
import { z } from "zod";

const Triage = z.object({
  category: z.enum(["billing", "technical", "other"]),
  urgency: z.enum(["low", "normal", "high"]),
  rationale: z.string().max(500),
});

const result = Triage.safeParse(JSON.parse(modelText));
if (!result.success) throw new Error("Model output did not match triage schema");
```

With the Responses API, pass a JSON Schema through the documented Structured Outputs mechanism. The example above illustrates application validation after receiving a response.

## Practice

1. Design a leave-request schema with dates, duration, and reason.
2. Add valid-date constraints in the business layer.
3. Test missing fields, invalid enums, and valid output that lacks authorization for execution.

## Common mistakes

- Confusing valid JSON with correct data.
- Overly permissive schemas with many optional fields.
- Retrying schema mismatches indefinitely.
- Using model output directly for SQL, shell commands, or access decisions.

## Interview questions

Original practice questions based on the primary references below, checked on 2026-11-07. These are preparation exercises, not verified questions from a particular employer. Design answers suggest one defensible approach. The literal \* Essential marker indicates editorial priority; start there before the follow-up questions.

### 1. \* Essential — How do JSON mode and Structured Outputs differ?

**Why essential:** A valid data contract is required before downstream code consumes model output.

**Answer outline:** JSON mode targets syntactically valid JSON; Structured Outputs constrain supported output to a supplied schema. Neither proves the business facts inside the fields are correct.

Reference: [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

### 2. When should you use function calling instead of a structured answer?

**Answer outline:** Use function calling to request application capabilities. Use a structured answer to return typed data to the user; application code still decides whether an action is authorized.

Reference: [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling).

### 3. What if generation refuses or stops before completion?

**Answer outline:** Treat refusal, incomplete generation, and schema-valid success as separate outcomes. Avoid executing side effects from partial data; surface a recoverable state and validate business constraints.

Reference: [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).
