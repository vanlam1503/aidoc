## Learning objectives

Explain why a tool call is a proposal, validate arguments, and distinguish read actions from write actions.

## Prerequisites

Complete the prerequisite lesson: [responses-api](/learn/responses-api). If you already know this material, use the practice questions to assess your understanding.

## Theory

When a model proposes a tool call, the application runs the loop: receive call → parse and validate arguments → authorize user and resource → execute tool → return the result to the model. A schema constrains format; it does not grant permissions. Keep tools small, contracts stable, and results structured.

## Architecture

Model proposes function and arguments → Zod parsing → authorization policy → handler with timeout → filtered output → continue response or request confirmation.

## TypeScript example

```ts
const Args = z.object({ orderId: z.string().regex(/^ORD-[0-9]{6}$/) });
const args = Args.parse(JSON.parse(rawArguments));
await assertCanReadOrder(session.user.id, args.orderId);
```

This snippet illustrates boundaries and data types. Before production use, add validation, error handling, and permissions appropriate to the use case.

## Practice

Design order-lookup and refund tools. Specify validation schemas, owner-based authorization, idempotency keys, and approval points.

## Common mistakes

Executing unparsed arguments; trusting a model-supplied order ID; exposing arbitrary shell or SQL; omitting timeouts or bounded retries.
