## Learning objectives

Explain why a tool call is a proposal, validate arguments, and distinguish read actions from write actions.

## Prerequisites

Complete the prerequisite lesson: [responses-api](/learn/responses-api). If you already know this material, use the practice questions to assess your understanding.

## Theory

When a model proposes a tool call, the application runs the loop: receive call → parse and validate arguments → authorize user and resource → execute tool → return the result to the model. A schema constrains format; it does not grant permissions. Keep tools small, contracts stable, and results structured.

## Architecture

Model proposes function and arguments → Zod parsing → authorization policy → handler with timeout → filtered output → continue response or request confirmation.

## TypeScript example

```ts
const Args = z.object({ orderId: z.string().regex(/^ORD-[0-9]{6}$/) });
const args = Args.parse(JSON.parse(rawArguments));
await assertCanReadOrder(session.user.id, args.orderId);
```

This snippet illustrates boundaries and data types. Before production use, add validation, error handling, and permissions appropriate to the use case.

## Practice

Design order-lookup and refund tools. Specify validation schemas, owner-based authorization, idempotency keys, and approval points.

## Common mistakes

Executing unparsed arguments; trusting a model-supplied order ID; exposing arbitrary shell or SQL; omitting timeouts or bounded retries.

## Interview questions

Original practice questions based on the primary references below, checked on 2026-11-07. These are preparation exercises, not verified questions from a particular employer. Design answers suggest one defensible approach. The literal \* Essential marker indicates editorial priority; start there before the follow-up questions.

### 1. \* Essential — What does a function call from the model actually do?

**Why essential:** Model-generated arguments must cross a validated application boundary before execution.

**Answer outline:** It requests an operation with arguments. Your application validates those arguments, checks authorization, executes the tool, and returns its result using the matching call identifier.

Reference: [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling).

### 2. Why does a strict tool schema not replace authorization?

**Answer outline:** A schema constrains shape, not user ownership or permitted effects. Check the authenticated actor and target resource beside the tool implementation, before a side effect occurs.

Reference: [MCP security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices).

### 3. A tool times out after creating an order. Should you retry?

**Answer outline:** First reconcile the operation status. Reuse a durable idempotency key supported by the downstream service; a lost acknowledgement does not prove the order was never created.

Reference: [AWS timeouts, retries, and backoff with jitter](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter).
