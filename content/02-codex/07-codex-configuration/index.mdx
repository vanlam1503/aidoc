## Learning objectives

Identify configuration scope, constrain tools, and explain how configuration affects agent behavior.

## Prerequisites

Complete the prerequisite lesson: [agents-md](/learn/agents-md). If you already know this material, use the practice questions to assess your understanding.

## Theory

Configuration may select a model, guidance, environment, and permissions. Prefer project settings that can be reviewed alongside code; avoid machine-wide changes for a local project need. Network, shell, and file-write permissions can have side effects, so document their purpose and verification.

## Architecture

Defaults → user configuration → project configuration → session constraints; effective permissions are bounded by policy, the runtime sandbox, and approvals.

## TypeScript example

```ts
type Permissions = { read: boolean; writePaths: string[]; network: "deny" | "allow" };
const projectPolicy: Permissions = { read: true, writePaths: ["src", "tests"], network: "deny" };
```

This snippet illustrates boundaries and data types. Before production use, add validation, error handling, and permissions appropriate to the use case.

## Practice

Design configuration for a docs-only repository and an application with tests. Compare permissions, scope, and risks of committing the configuration.

## Common mistakes

Copying configuration without understanding permissions; requesting broader project access than necessary; committing credentials.

## Interview questions

Original practice questions based on the primary references below, checked on 2026-11-07. These are preparation exercises, not verified questions from a particular employer. Design answers suggest one defensible approach. The literal \* Essential marker indicates editorial priority; start there before the follow-up questions.

### 1. \* Essential — Can project configuration weaken an enforced organization policy?

**Why essential:** Effective permissions must be understood before changing configuration.

**Answer outline:** No. Enforced requirements constrain allowed behavior; ordinary configuration supplies defaults. Diagnose the active policy and project trust before changing a local setting.

Reference: [Codex configuration basics](https://learn.chatgpt.com/docs/config-file/config-basic).

### 2. Where would you put personal defaults and project overrides?

**Answer outline:** User defaults live in ~/.codex/config.toml; trusted projects can add .codex/config.toml layers. More specific settings and CLI overrides still remain subject to enforced requirements.

Reference: [Codex configuration basics](https://learn.chatgpt.com/docs/config-file/config-basic).

### 3. Why is disabling approval prompts different from granting full access?

**Answer outline:** Approval review and sandbox capabilities are separate controls. A command can remain blocked by filesystem or network limits even when the agent will not ask for escalation.

Reference: [Codex permission modes](https://learn.chatgpt.com/docs/permission-modes).
