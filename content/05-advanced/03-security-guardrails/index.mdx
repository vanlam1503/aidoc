## Learning objectives

Draw a threat model, distinguish input/output checks from access control, and define fail-closed behavior.

## Prerequisites

Complete the prerequisite lesson: [prompt-injection-fundamentals](/learn/prompt-injection-fundamentals). If you already know this material, use the practice questions to assess your understanding.

## Theory

Guardrails span authentication, authorization, input/output validation, tool allowlists, data minimization, human review, and monitoring. Model moderation and classification are supplementary signals. Threat models must consider users, RAG content, tool output, tenant boundaries, and consequential actions.

## Architecture

Untrusted input → validation and classification → least-privilege tools → policy check per call → output filtering → audit and incident response.

## TypeScript example

```ts
type PolicyDecision = "allow" | "deny" | "review";
function decide(action: string, amount: number): PolicyDecision {
  if (action === "refund" && amount > 0) return "review";
  if (!["lookup", "draft", "refund"].includes(action)) return "deny";
  return "allow";
}
```

This snippet illustrates boundaries and data types. Before production use, add validation, error handling, and permissions appropriate to the use case.

## Practice

Threat-model an agent that reads orders and creates refunds. Draw trust boundaries, user permissions, approval thresholds, and an incident scenario.

## Common mistakes

Treating a system prompt as a sandbox; trusting model-supplied user IDs; filtering output while omitting server authorization.

## Interview questions

Original practice questions based on the primary references below, checked on 2026-11-07. These are preparation exercises, not verified questions from a particular employer. Design answers suggest one defensible approach. The literal \* Essential marker indicates editorial priority; start there before the follow-up questions.

### 1. \* Essential — Why are model instructions insufficient as an access-control system?

**Why essential:** Authorization at the side-effect boundary limits the impact of model mistakes.

**Answer outline:** The model can misunderstand or follow malicious content. Enforce identity, ownership, allowed operations, and least privilege in server-side tools before accessing or changing data.

Reference: [OWASP excessive agency (2025 edition)](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/).

### 2. What does a guardrail do, and where should it run?

**Answer outline:** It checks a defined condition, such as disallowed input or a risky tool request. Place effect-specific validation next to execution; agent-level checks do not cover every intermediate action.

Reference: [Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals).

### 3. How would you protect an agent running on a pull request from a fork?

**Answer outline:** Treat code and event fields as untrusted. Use restricted credentials and isolated execution, avoid exposing secrets to untrusted jobs, and separate verification from privileged publishing.

Reference: [GitHub Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use).
