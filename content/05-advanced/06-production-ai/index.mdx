## Learning objectives

Design a release pipeline, check secrets and migrations, and define rollback for model behavior changes.

## Prerequisites

Complete the prerequisite lesson: [observability](/learn/observability). If you already know this material, use the practice questions to assess your understanding.

## Theory

AI deployment versions include code, prompts, model configuration, retrieval indexes, and evaluators. CI should run type checks, unit/integration tests, content/evaluation gates, and secret scans. A staged rollout exposes limited traffic while monitoring cost, latency, refusals, and quality. Database changes need backward compatibility so the application can roll back.

## Architecture

Commit → CI checks and evaluations → build artifact → staging smoke tests and canary → approve promotion → monitor SLOs and quality → roll back version, configuration, or index.

## TypeScript example

```ts
type Release = { app: string; promptVersion: string; model: string; indexVersion: string };
const release: Release = { app: "1.8.0", promptVersion: "support-v12", model: "configured-model", indexVersion: "kb-2026-10-31" };
```

This snippet illustrates boundaries and data types. Before production use, add validation, error handling, and permissions appropriate to the use case.

## Practice

Write a release checklist for a prompt change alongside a database schema change. Select canary metrics, rollback triggers, and compatibility checks for an older index.

## Common mistakes

Deploying unversioned prompt changes; overlooking API key rotation; applying destructive migrations without a recovery plan.

## Interview questions

Original practice questions based on the primary references below, checked on 2026-11-07. These are preparation exercises, not verified questions from a particular employer. Design answers suggest one defensible approach. The literal \* Essential marker indicates editorial priority; start there before the follow-up questions.

### 1. \* Essential — What should be versioned for an AI release?

**Why essential:** A release must be observable and reversible before receiving broad traffic.

**Answer outline:** Version application code, prompt, model configuration, retrieval settings, and evaluation data. Keep the release artifact identifiable so a regression can be compared and rolled back.

Reference: [Google SRE canary releases](https://sre.google/workbook/canarying-releases/).

### 2. How do you handle credentials and environment separation?

**Answer outline:** Keep API credentials server-side, use a secret manager or environment variables, and isolate staging from production with restricted service identities and budgets.

Reference: [OpenAI production best practices](https://developers.openai.com/api/docs/guides/production-best-practices).

### 3. Why combine offline evaluation with a canary rollout?

**Answer outline:** Offline gates catch known failures; a small controlled rollout reveals behavior on live traffic. Define monitoring and rollback conditions before increasing exposure.

Reference: [Google SRE canary releases](https://sre.google/workbook/canarying-releases/).
