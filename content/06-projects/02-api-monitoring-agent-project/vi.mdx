## Mục tiêu học tập

Tách detection rule khỏi LLM summary; giới hạn tool; thiết kế dedupe và escalation policy.

## Điều kiện tiên quyết

Hoàn thành bài liên quan trước đó: [agent-orchestration](/learn/agent-orchestration). Nếu đã biết phần này, hãy dùng câu hỏi thực hành để tự đánh giá.

## Lý thuyết

Monitoring agent nên dùng deterministic checks để phát hiện ngưỡng availability/latency. LLM có thể tổng hợp log đã lọc, gợi ý runbook và soạn incident update; không nên tự restart hệ thống hay đổi traffic nếu chưa có policy/phê duyệt. Dedupe tránh spam và incident phải có trace.

## Kiến trúc

Metrics alert → incident state/dedupe → retrieve runbook → summarize evidence with timestamps → propose action → human approval → audit/close.

## Ví dụ TypeScript

```ts
type Incident = { key: string; severity: "warning" | "critical"; observedAt: string; evidence: string[] };
function dedupeKey(i: Incident) { return `${i.key}:${i.severity}`; }
```

Đây là đoạn minh họa ranh giới/kiểu dữ liệu; trước production cần bổ sung validation, error handling và quyền phù hợp với use case.

## Thực hành

Dựng tabletop cho tăng latency và 5xx. Viết deterministic trigger, thông tin được đưa vào model, thông báo on-call và hành động bị cấm tự động.

## Lỗi thường gặp

Để model tự phát hiện mọi outage; đưa secret header vào log; không chống alert storm hoặc nhầm dữ liệu cũ.

## Câu hỏi phỏng vấn

Câu hỏi luyện tập tự biên soạn từ các nguồn gốc bên dưới, kiểm chứng ngày 2026-11-07. Đây là bài tập ôn phỏng vấn, không phải câu hỏi được xác nhận từ một nhà tuyển dụng cụ thể. Đáp án thiết kế gợi ý một cách tiếp cận có cơ sở. Dấu \* Essential thể hiện mức ưu tiên biên tập; ôn câu này trước các câu tiếp theo.

### 1. \* Essential — Khi cảnh báo API phát, agent nên nhận gì?

**Vì sao cần ưu tiên:** Telemetry xác định cần xác lập sự cố trước khi agent đề xuất khắc phục.

**Gợi ý trả lời:** Cung cấp dịch vụ bị ảnh hưởng, khoảng thời gian, triệu chứng, số đo độ trễ và lỗi cùng định danh trace. Tách quan sát thực tế khỏi giả thuyết nguyên nhân.

Nguồn kiểm chứng: [Google SRE monitoring](https://sre.google/sre-book/monitoring-distributed-systems/).

### 2. Agent có nên tự restart dịch vụ production không?

**Gợi ý trả lời:** Chỉ trong policy khắc phục được cấp quyền rõ ràng. Bắt đầu bằng chẩn đoán chỉ đọc, giới hạn tool và xét duyệt hành động gây gián đoạn; cảnh báo không tự cấp quyền ghi.

Nguồn kiểm chứng: [OWASP excessive agency (2025 edition)](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/).

### 3. Bạn chứng minh monitoring agent hoạt động thế nào?

**Gợi ý trả lời:** Tạo tình huống chậm và lỗi có kiểm soát, lần theo trace rồi so chẩn đoán với nguyên nhân đã biết. Kiểm tra gộp cảnh báo, thời điểm chuyển cấp và dữ liệu xác nhận khôi phục.

Nguồn kiểm chứng: [OpenTelemetry traces and spans](https://opentelemetry.io/docs/concepts/signals/traces/).
