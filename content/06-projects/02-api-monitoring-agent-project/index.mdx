## Learning objectives

Separate detection rules from LLM summaries, constrain tools, and define deduplication and escalation policy.

## Prerequisites

Complete the prerequisite lesson: [agent-orchestration](/learn/agent-orchestration). If you already know this material, use the practice questions to assess your understanding.

## Theory

A monitoring agent should detect availability and latency thresholds with deterministic checks. An LLM can summarize filtered logs, suggest runbooks, and draft incident updates; restarting systems or rerouting traffic requires explicit policy and approval. Deduplicate alerts to prevent spam and preserve incident traces.

## Architecture

Metric alert → incident state and deduplication → retrieve runbook → summarize timestamped evidence → propose action → human approval → audit and close.

## TypeScript example

```ts
type Incident = { key: string; severity: "warning" | "critical"; observedAt: string; evidence: string[] };
function dedupeKey(i: Incident) { return `${i.key}:${i.severity}`; }
```

This snippet illustrates boundaries and data types. Before production use, add validation, error handling, and permissions appropriate to the use case.

## Practice

Run a tabletop exercise for increased latency and 5xx errors. Define deterministic triggers, model input, on-call messages, and actions forbidden from automatic execution.

## Common mistakes

Expecting a model to detect every outage; logging secret headers; allowing alert storms or using stale evidence.

## Interview questions

Original practice questions based on the primary references below, checked on 2026-11-07. These are preparation exercises, not verified questions from a particular employer. Design answers suggest one defensible approach. The literal \* Essential marker indicates editorial priority; start there before the follow-up questions.

### 1. \* Essential — What should the agent receive when an API alert fires?

**Why essential:** Deterministic telemetry should establish an incident before an agent proposes remediation.

**Answer outline:** Provide the affected service, time window, symptoms, latency/error metrics, and relevant trace identifiers. Keep observations separate from hypotheses about the root cause.

Reference: [Google SRE monitoring](https://sre.google/sre-book/monitoring-distributed-systems/).

### 2. Should the agent automatically restart a production service?

**Answer outline:** Only within an explicitly authorized remediation policy. Start with read-only diagnosis, bound tool capabilities, and require review for disruptive actions; an alert alone does not grant write access.

Reference: [OWASP excessive agency (2025 edition)](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/).

### 3. How would you demonstrate the monitoring agent works?

**Answer outline:** Inject controlled latency and failure scenarios, follow traces, and compare diagnosis with known causes. Check alert deduplication, escalation timing, and whether recovery claims match observed metrics.

Reference: [OpenTelemetry traces and spans](https://opentelemetry.io/docs/concepts/signals/traces/).
