## Learning objectives

Build a read-only review pipeline, cite files and lines, and measure precision on sample diffs.

## Prerequisites

Complete the prerequisite lesson: [codex-workflows](/learn/codex-workflows). If you already know this material, use the practice questions to assess your understanding.

## Theory

A code review agent needs bounded context: the diff, repository guidance, and relevant tests. Findings require severity, location, reproduction conditions, and evidence. Keep the first project read-only rather than allowing edits or merges; focus on triage, false-positive measurement, and an audit trail.

## Architecture

Git diff → context pack with changed files, nearby code, and rules → model analysis → schema validation → path/line verification → report → human triage.

## TypeScript example

```ts
type ReviewFinding = { severity: "high" | "medium" | "low"; file: string; line: number; evidence: string; suggestion: string };
function inChangedFile(f: ReviewFinding, changed: Set<string>) { return changed.has(f.file); }
```

This snippet illustrates boundaries and data types. Before production use, add validation, error handling, and permissions appropriate to the use case.

## Practice

Create a fixture with one real bug and two distractors. Score finding precision, path validity, severity, and reproducibility. Keep the agent read-only.

## Common mistakes

Sending the entire repository; citing nonexistent lines; allowing unreviewed commits of proposed fixes.

## Interview questions

Original practice questions based on the primary references below, checked on 2026-11-07. These are preparation exercises, not verified questions from a particular employer. Design answers suggest one defensible approach. The literal \* Essential marker indicates editorial priority; start there before the follow-up questions.

### 1. \* Essential — What makes an automated review finding actionable?

**Why essential:** Review findings need evidence before they can justify a code change.

**Answer outline:** Identify the affected code, concrete trigger, incorrect behavior, and impact. Provide a reproduction or clear reasoning grounded in the diff; distinguish evidence from uncertainty.

Reference: [Code review and evidence](https://learn.chatgpt.com/docs/code-review).

### 2. Why is reviewing a pull request also an execution-security problem?

**Answer outline:** Repository code, scripts, and PR text may be attacker-controlled. Inspect without privileged secrets and isolate any test execution; do not let untrusted content authorize publishing or data access.

Reference: [GitHub Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use).

### 3. How would you evaluate false-positive review comments?

**Answer outline:** Create labeled diffs with real bugs and harmless changes. Measure finding precision, missed important defects, and evidence quality, rather than rewarding the number of comments.

Reference: [LangSmith Evaluation](https://docs.langchain.com/langsmith/evaluation).
